Nota 1 — ¿Por qué el APK con CoreCLR pesa más?

Al compilar .NET MAUI para Android en Release, se elige entre Mono (runtime histórico, optimizado para mobile) y CoreCLR (runtime moderno de .NET, portado recientemente a mobile).

Razones del mayor tamaño

Runtime más pesado por diseñoCoreCLR fue construido para desktop/server y luego portado. Mono fue diseñado desde el inicio para dispositivos embebidos y móviles.
AOT genera .so más grandesCon CoreCLR, el compilador AOT produce archivos nativos de mayor tamaño. Mono usa un modelo AOT más compacto e interpreta parte del IL.
Trimming menos maduro en mobileEl linker no es igual de agresivo con CoreCLR. Mono lleva años con optimizaciones de tamaño específicas para mobile.
Mayor porción del BCL empaquetadaCoreCLR tiende a incluir más del Base Class Library en el bundle, reducible con trimming agresivo.

Cómo reducir el tamaño con CoreCLR

<PublishTrimmed>true</PublishTrimmed>
<TrimMode>link</TrimMode>
<AndroidCreatePackagePerAbi>true</AndroidCreatePackagePerAbi>
<AndroidUseAapt2>true</AndroidUseAapt2>
<AndroidEnableAssemblyCompression>true</AndroidEnableAssemblyCompression>
ConclusiónCoreCLR prioriza rendimiento sobre tamaño. El mayor peso del APK es un trade-off esperado. Microsoft está trabajando activamente en reducirlo.

Nota 2 — Benchmark: Lista virtual con 10.000 items

Página BenchmarkListPage en la app de sample, accesible desde el menú hamburguesa (sección Benchmarks). Carga 10.000 items desde JSON pre-generado (~1.5 MB) y mide 4 fases por separado.

FaseOperación
1. JSON deserializeJsonSerializer.Deserialize<List<BenchmarkRawDto>>()
2. LINQ map + sortProyección DTO → modelo + OrderByDescending(score)
3. Date parse + formatDateTime.Parse + .ToString("MMM dd, yyyy") × 10k
4. Bind collectionnew ObservableCollection<BenchmarkItem>(list)

Por qué estas fases muestran diferencias

  • JSON deserialize — System.Text.Json se beneficia del JIT de CoreCLR en code paths repetitivos.
  • LINQ + proyección — CoreCLR optimiza mejor iteradores y lambdas en caliente.
  • Date parse/format — Operaciones de string intensivas; GC e inlining marcan diferencia.
  • Bind collection — Overhead del constructor de ObservableCollection y notificaciones.

Archivos involucrados

  • Models/BenchmarkItem.cs
  • Models/BenchmarkRawDto.cs
  • ViewModels/BenchmarkListViewModel.cs
  • Pages/BenchmarkListPage.xaml

Nota 3 — CoreCLR es estricto con coerción de tipos en bindings

Con x:DataType en un DataTemplate (bindings compilados), el tipo del modelo debe coincidir exactamente con el del control.

Ejemplo que falla en CoreCLR pero funciona en Mono
<DataTemplate x:DataType="models:BenchmarkItem">
  <!-- Score es int, Text espera string -->
  <Label Text="{Binding Score}" />
</DataTemplate>
MonoConversión int → string implícita vía BindingExpression. No explota.
CoreCLRBinding compilado asigna int directamente a string → InvalidCastException envuelta en TargetInvocationException.

Síntoma en logcat

android.runtime.JavaProxyThrowable: [System.Reflection.TargetInvocationException]:
  Exception has been thrown by the target of an invocation.
  at BindingExpression+BindingExpressionPart.TryGetValue
  at ...BenchmarkListPage+<>c.<InitializeComponent>b__1_1

El inner exception real (InvalidCastException) no aparece en logcat — solo el wrapper. Difícil de diagnosticar.

Fix recomendado

Opción A: StringFormat
<Label Text="{Binding Score, StringFormat='{0}'}" />
Opción B (recomendada)
<Label Text="{Binding ScoreText}" />
Regla general para CoreCLREn bindings compilados con x:DataType, el tipo de la propiedad del modelo debe coincidir exactamente con el del control. No asumir coerción implícita.

Tipos problemáticos: int/double/float → string (Label.Text), Color struct vía reflexión, bool → string sin converter.

Ejemplo: 200 partículas → 4.200 draw calls/frame → ~250k draw calls/segundo a 60 fps. Loop vía InvalidateSurface() al final de cada PaintSurface.

MétricaDescripciónPor qué importa
FPSFrames por segundo del frame actualReferencia instantánea, muy variable
avg FPSPromedio móvil de los últimos 120 framesNúmero más representativo del rendimiento sostenido
min FPSMínimo histórico desde el inicioRevela GC pauses y JIT stalls
physics msLoop C# por frame: posiciones, bordes, trailRendimiento JIT sobre código numérico puro
draw msSkia canvas: N × 21 DrawCircle() con paint/alphaOverhead del interop .NET → Skia nativo

Comandos de compilación

CoreCLR
dotnet build -f net11.0-android -c Release -p:UseMono=false
Mono
dotnet build -f net11.0-android -c Release -p:UseMono=true

Protocolo de medición

  1. Abrir app → Benchmarks → Skia particles animation
  2. Seleccionar nivel de carga (50 / 100 / 200 / 500)
  3. Start → esperar ~30 s para estabilizar JIT
  4. Anotar: avg FPS, min FPS, physics ms, draw ms
  5. Repetir en la otra app (mismo dispositivo)
